## 1. 判断

**建议采用 harness2 作为离线优化引擎，先稳定实验环境与执行契约，再测基线、做小范围试点，依据问题归因决定继续培养或先补能力。** 现有 PydanticAI、DAG、结构化结果和确定性报告可以继续使用。

需要区分两个里程碑：

- **接入优化引擎**：让 harness2 改进当前 Analyzer、Reviewer、Reviser 的分析与复核策略，并验证改进是否能迁移到其他样本。这个里程碑不依赖主动补料工具，也不要求先重写执行框架。
- **扩展第三阶段 Agent 能力**：让 Agent 主动查材料、补证据、做跨包语义复核。这会扩大现有 Worker 的权限与调用次数，必须另补材料来源、工具预算和审计契约。它能扩大后续优化空间，但不是第一次接入的必要条件。

当前实际执行链是材料包 DAG、逐包 Analyzer→Reviewer→条件 Reviser、全局 ID 关系整理、程序生成报告。`final_assessment=None`；末端没有执行中的自由分析/最终语义评估模型。harness2 只能优化实际存在且被执行器消费的部分，不能靠修改提示词补出一个不存在的工具或分析节点。[E2、E4]

环境准备列为步骤 0：此前已核实 Windows 虚拟环境为 Python 3.14.0，而固定版本 harness2 声明 `>=3.12,<3.14`、README 推荐 Linux；本项目声明 `>=3.11`。兼容性必须在目标培养环境验证，不能凭声明认定。[E10、H5]

对本次顺序建议的取舍：环境前置、校准后移、输入准备提前、增加决策关口、生产审计修复独立，均采纳；“每份报告受影响”“B/C/D 代码互不依赖”“只有一个任务经验库完全无用”“测一次基线后永远可用”不作为事实。正常 DAG 会传材料，多个同源子图仍可传递经验但不能证明跨样本泛化；模块共用工作流，能力和输入改变会改变比较条件。[E2、E4、E12、H4]

### 0. 建立培养环境，同时启动输入准备

在 Linux/WSL 的 Linux 文件系统内建立独立培养目录和 Python 3.12 环境，优化器、编辑/选择 CLI 与第三阶段都在其中运行。WSL 培养目录优先放在 Linux 用户目录，避免执行时反复跨 `D:/` 与 `/mnt/d` 边界；Windows 现有环境继续正常分析，B/C/D 的开发与单元检查也可在那里进行，正式校准只能在已固定的培养环境完成。

先验证依赖安装、模块加载和离线测试可执行，复现并登记当前已知失败；A 中对齐测试及修复审计后，再在同一目标环境通过相关回归，作为 E-2 的入口。这样不会出现“0 要测试全绿，A 才修旧测试”的循环依赖。编辑通道先做 CLI 启动、配置、凭据与预检；必要的真实服务冒烟调用单列预算，不启动完整模型链。

**样本准备线从此时开始，贯穿 E/F。** 建议先列 5–10 个方向不同的独立样本输入清单，优先取得 2–3 个训练样本和至少 1 个留出样本的可用材料。数量是首批供给目标，不是证明收益所需的统计保证；1 个留出样本只能支持很初步的迁移判断。E 的接口与单样本试点无需等全部样本就绪，F 的跨任务合并与留出验证则必须等到相应输入真正可用。

当前代码只消费已导出的材料和 manifest，不能从本目录断言所有新样本都必须重跑第一、第二阶段。可由现有上游流程产出，也可接收已有的合规导出；本轮不进入上游目录改代码。每份输入应具备：独立样本 ID、符合当前解析契约的 `J*.md`、稳定函数标识和原始 `L` 行号、无缺失依赖/环且数量一致的 manifest、材料清单与摘要。包数可以不同，不要求复制 16 包结构。[E8、E11、E14]

在任何任务优化前按原样本划分训练/留出，近重复与相关样本同组；逐步补充行为/条件/IOC 标注并扩充覆盖面。标签、人工答案与评分留在评估侧。20–50 个样本仍是后续建设目标，不设成环境搭建或接口接线的前置条件。

### A. 固定可比较的基线与实验边界

1. 保存当前 Git 提交、工作区差异，以及配置、提示词、schema 版本和输入清单的快照/摘要；本轮已检测到 Git 元数据，不再沿用早先“无 Git”的环境判断。包含未提交改动的实际执行内容也必须进入实验版本，不能只记提交号。
2. **正式支持两种任务：整样本 `sample` 和依赖闭合子图 `closed_subgraph`。** 优化试点先用较小子图，发布验收使用整样本。子图必须递归包含目标包的所有 `depends_on` 祖先，生成独立 manifest 和材料白名单，候选与基线每次都重跑这些包，避免复用基线的依赖摘要影响归因。当前 J00–J15 是同一样本的 16 个关联作业；不同子图仍属于同一样本，训练/留出必须按原样本分组。[E4、E8、E11]
3. 固定模型、分析预算、材料、DAG 和报告代码，再比较 harness。不要同时换模型、扩大输入和改提示词，否则无法解释收益来源。
4. 对齐当前三项测试中的旧配置/旧版本断言，得到明确、可重复的基线。这属于接入前准备；本轮没有改测试或业务代码。

**本步不运行模型基线校准。** 原包资源加载路径与 B 的快照加载路径不同，D 的统一指标也未完成；正式测量后移到 E-1 替身验证通过之后。A 只定义比较条件和任务类型，诊断后才决定具体试点子图。

此前仅验证过图依赖示例：目标 J04 的闭包是 J00、J01、J04，三包 manifest 可通过当前 DAG 校验。本轮再次核对闭包一致，但它仍不是按当前问题分布选出的试点。包内容与调用量不同，不能按 3/16 直接推算节省比例。

**独立处理生产审计缺陷。** 当前未提供源码目录或目录内没有 J 材料时，引用审计实际返回 `not_run/passed=true`，可能使报告和 `completed` 被标为完成。正常 DAG batch 会传入材料目录；风险可由无材料的 `assess/report`、`reconcile` 和直接调用投影函数触发，不能泛称每份现有报告都受影响。[E5、E12]

建议作为独立小补丁修改 `knowledge_report.py` 及受影响的完成状态传播：未运行引用审计必须明确标记，不能成为通过/完整的依据；没有源码时仍可导出未核验报告与原有事实，不必粗暴禁用离线阅读。保留“审计执行过但引用不合格”与“根本没执行”的区别，不改变候选质量相对比较规则。

补丁验收至少覆盖：无材料、空目录、合法引用、失效引用，以及 CLI 汇总 `completed` 与底层状态一致；既有测试中无源码却断言总审计通过的用例需调整，保留其来源/分层等原有断言或改用合法材料夹具，不能只删除测试。生产修复有独立版本、回归和发布记录，可在现有支持环境先推进，不被 Linux 优化器准备阻塞。本轮只是提出该补丁，未改代码或上线。

在分工 B/C/D 前先固定三个接口：B 返回本次实际指令、冻结规则及版本摘要；C 以稳定 run/task/packet/stage/event ID 记录输入、输出和程序决定；D 从规范产物与材料快照计算“审计是否执行、流程完整性、质量指标”。运行清单同时登记环境/依赖、代码、模型、预算、任务/材料、基线 harness 和指标版本，作为同一轮比较的身份。

B/C/D 可按这些契约分工，但不能声称代码互不依赖：B 要改 Workflow 构造与指令组合，C 要改同一个 Workflow 的调用与修订记录，D 复用校验产物并接报告入口。共享文件改动按顺序整合，合并后再联调；新 `delivery_gate.py` 或 `trajectory.py` 文件本身不能消除调用方依赖。[E1、E2、E4]

验收：同一份输入和指定版本的 harness 能在独立目录重复运行；每个结果能追溯到实际指令、材料和模型配置。这里的“重复”指配置与输入可复现，不要求模型逐字一致。

### B. 补运行级 harness 加载，限定真正可优化的内容

主要改动点：`prompts.py`、`BoundedInvestigationWorkflow.__init__()`、CLI/config；建议新增小型 `harness_loader.py`，集中处理路径、映射、校验和指令组合。[E1、E2]

首轮只开放 **Analyzer/Reviewer/Reviser 的分析策略文本**，例如核对顺序、source→action→sink 分析方法、函数语义识别提示和防漏查策略。全局整理策略以后单独做实验，便于归因。

以下内容由受信代码固定注入或执行：公共证据规则、输出 schema、输入模板中的必需字段、复核触发阈值、修订范围、IOC 分流、引用与来源审计、预算和报告生成。不能只在一个可编辑文件里写“不可修改”，然后仍允许优化器重写它。

**本步实现项目自身的加载与策略契约，不依赖 harness2 安装。** 共享策略放 `systemprompt.md`，三个必需角色定义放 `agents/analyzer.md`、`agents/reviewer.md`、`agents/reviser.md`；领域知识放 `skills/<name>/SKILL.md`，只能注入这三个角色的分析上下文，不能扩展执行器权限。角色 frontmatter 只声明匹配的 name；skill 需包含匹配目录的 name、description 和非空 roles。加载器按固定顺序拼接适用策略，限定文件数、单文件和总长度；超限拒绝，不能无声截断或忽略。未来 E-1 的原生文件面须按实际目录映射，不能沿用旧版把角色当作三个 skill 的约定。

这些 skill 由程序按角色装载，不存在 `skill/task/Bash` 工具循环；首轮禁止 script、plugin、subagent 和未实现的记忆/工具组件。B 固定可加载路径与元数据，E-1 再据此注册原生文件面和配置触发行，避免文件面设计倒逼加载器改变权限。

需要落实的约束：

- `--harness-dir` 对整次 batch 固定，逐包构造 Workflow 时传入同一个已验证快照；禁止改安装包内的提示词实现切换，否则并行候选会相互污染。
- 角色与领域 skill 首轮均按 roles 确定性加载，不声称已有模型自主检索或按需工具功能。
- 声明哪些文件实际会被加载；编辑未支持的脚本、plugin、subagent、工具指导或记忆文件应拒绝，不能接受后悄悄忽略。
- 校验路径、链接逃逸、文件数量与长度、skill 格式和必需角色；失败在调用模型前报出可修正的原因。
- 将实际组合后的 instructions、harness 摘要及冻结规则版本保存到运行目录。

冻结规则从可信资源固定注入，并为后续编辑模型提供同版本的只读说明和摘要：公共证据规则、复核阈值、IOC 分流及材料边界都必须可见。候选策略不得覆盖它们，编辑器上下文副本也不得传回执行器；冻结资源版本不匹配时拒绝。具体复制到 `source/frozen_rules.md`、注入 `BenchPrompts` 的接线在 E-1 完成。[E1、H1]

项目校验器可拒绝少量明确的冲突表述，例如直接要求跳过引用核查或将无证据猜测升级为确认；检查要区分否定、引述和正向指令，遇到难判情况保留诊断供审核。关键词检查只能辅助，不能证明任意自然语言策略与规则一致，最终仍靠受信程序约束及行为复验；E-1 的 `validate_tree()` 复用这一校验，不复制一套规则。

验收：基线快照经加载器生成的角色指令与原包资源指令语义一致，保留所有必需规则并保存实际文本；修改 Analyzer 策略只影响指定候选的 Analyzer，Reviewer/Reviser 各读取自己的策略；候选不能修改 schema、审计或执行器源码。由 E-1 检查 `execute(None)` 与显式基线路径一致。

### C. 补可用于改进的轨迹

建议新增 `trajectory.py`，在现有阶段执行与程序决策处记录事件，再渲染为 harness2 的 `[ACTION]/[OBSERVATION]/[ERROR]` 文本。当前 `_run_agent()` 已有集中调用点，可以复用。[E2、E3]

至少记录：

- `run_id/task_id/packet_id/stage/event_id`，实际 instructions、prompt、材料与依赖摘要的快照或可定位引用；
- Analyzer 输出、引用校验结果、原始与 scope guard 后的 Reviewer 决定、修订授权、Reviser 输出、实际采用/拒绝的修订及原因；
- Format Repair、结构化失败、部分保留、超时、全局来源校验和报告审计；
- 各阶段请求量、token、耗时；价格未配置时保留未知，不把未知成本记为零。

记录模型交付的结果与程序事件即可，不需要索取或补造模型私有思维过程。长日志可分文件，渲染时要保留稳定事件定位和截断提示，避免编辑模型因看不全材料而“发现”并不存在的问题。

**轨迹文件开头增加问题索引**：列出审计失败、Reviewer major/critical、修订被拒、格式修复失败对应的 event_id、包、阶段和详情位置；正文仍保存完整事件顺序。harness2 会把轨迹写入 `context/rollouts/*.md`，索引必须出现在该渲染文件内，不能只留在外部原始日志中。索引按事实定位，不混入隐藏标签或离线评分。[H9]

验收：每条改动建议都能指到具体运行、包和事件；同一个事件可还原当时看到的材料与实际输出。

### D. 分离流程完整门槛与证据质量

建议新增 `delivery_gate.py`，在 A 的报告缺陷修复之上产出流程检查和证据质量摘要；由可信代码读取本次材料与结构化产物重算，不能采用模型自写的 `passed=true`。本步不另造生产 not_run 修复，也不依赖 harness2 包；E-1 的适配器再调用它。两个结果用途不同：

| 层 | 检查内容 | 使用位置 |
|---|---|---|
| 流程完整：硬门槛 | 当前任务 manifest 所有预期包有 schema 合法的产物且完成规定复核；必要阶段按约定执行或合法保留原结果；全局来源账本结构完整；审计确实运行；版本、输入和冻结规则一致 | `delivered()`，不通过的候选不能进入选择池 |
| 证据质量：相对门槛 | 失效引用数与比例、引用总量、缺有效引用的 confirmed、受证据支持的核心事实保留情况、未解决复核问题及修订拒绝 | 可读产物与轨迹、选择后的 `score()`、独立发布比较 |

流程硬门槛的细节：

1. 以 sample 或 closed_subgraph 自己冻结的 manifest 判断覆盖；子图产物须明确标记范围，不能冒充整样本报告。DAG 中“任务成功”不等于已完成复核。
2. 检查报告与本次全局结果、输入和 harness 快照一致；来源账本中的来源缺失、重复冲突和数量不匹配属于结构错误。证据语义或引用质量问题另列，不把它们都合并成流程错误。
3. 对当前任务全部实际材料执行引用审计；材料目录缺失、空目录、审计异常或结果不可解析均拒绝，`status=not_run` 一律拒绝。审计执行过与审计通过分开判断。
4. 复核已完成但仍有重大质量问题，或程序拒绝修订并按约定保留有效初稿时，记录其质量/降级状态；不因它们一律禁止进入试验池。必需阶段缺失、流程中断或无可消费结果仍拒绝。

**不要用 `report.status == complete`、`knowledge_audit.passed` 或“零失效引用”直接决定 `delivered()`。** 当前 knowledge audit 同时汇总结构与证据质量；需分别计算，不能用总布尔值代替分类。此前记录的旧产物曾有 36 段失效引用、10 条缺有效引用的 confirmed；本轮 `results_v17` 目录已不存在，这些只作历史反例，正式基线需在 E-2 重新取得并检查完整流程。

可读产物展示每次审计的原始数量、分母及明细，供编辑/反思和有选择模型时参考；由适配器根据原始产物统一计算，避免模型自行挑选口径。只包含执行器本身可见的事实核查，不包含隐藏标注或离线评分。**k=1 没有选择模型**，把指标写进 `deliverable_text` 并不会自动产生质量择优，候选仍需外层重复比较和发布验收。[H3]

发布以预先约定的关键质量指标不差于基线、且有可重复收益为准，并检查保留基线中有材料支持的核心事实，防止靠少下结论改善引用数字。允许依据证据纠正错误结论、降级推断或合并等价表述，但需记录理由；条数减少本身不代表漏报。无标签时该保留检查仍有语义局限，不能冒称召回率已得到保障。

“零失效引用”保留为长期质量目标。若以后设置绝对发布下限，应先建立能通过的基线并明确规则，不能让优化试点在没有可比较起点时全部失去候选。流程不完整的失败候选和质量不足的完整候选都留档；只有经过发布流程的版本进入正常分析。

验收要同时验证两类反例：缺材料却返回 `complete`、仅有报告、漏包、未复核或冻结规则变化必须被拒；流程完整且仍有失效引用的候选应能进入试验池，同时如实暴露质量问题；靠删除有证据支持的核心事实改善引用数字的候选不得发布。引用自动窄修复可另设预算，首轮不必先实现。

### E-1. 实现 MalwareAdapter 和原生文件面，先跑执行替身

建议把集成放在独立的 `integrations/harness2/` 下，使当前正常分析入口不依赖优化器。以下是接口职责，尚非已完成实现。

| 接口 | 本项目应提供的内容 |
|---|---|
| `tasks(split)` | 固定 sample/closed_subgraph 任务及训练/留出划分；同源样本的所有子图同属一个划分 |
| `domain_of(task_id)` | 首轮用预先确定的单一 `static-code` 域；有足够样本后再用已提供的文件类型等元数据细分，禁止使用事后家族结论 |
| `task_prompt()` | 合法分析任务与材料边界，不包含标准答案、评分规则或模型需要命中的结论 |
| `task_files()` | 白名单导出的任务 manifest、闭合材料包、必要说明及只读 frozen_rules；绝不返回项目根目录 |
| `base_harness()` | 已发布基线的不可变快照，内容与 `execute(None)` 实际使用的基线一致 |
| `validate_tree()` | 原生文件面、角色/领域 skill 元数据和长度、冻结资源版本、明确冲突与可消费性检查；不支持的组件直接拒绝 |
| `execute()` | 指定 harness，在同一 Linux 培养环境执行当前任务的 DAG/全局/报告流程，输出到独立 run_id；恢复时核对任务范围及输入摘要 |
| `trajectory()` | 开头提供问题事件索引，按 obs_trunc 渲染正文并保留事件 ID |
| `delivered()` | 仅调用 D 的流程完整硬门槛；不以失效引用数、质量总 passed 或报告状态直接判失败 |
| `deliverable_text/files()` | 报告、结构化事实与统一计算的事实核查摘要，保留条件、限制、引用、分母和未解决问题；不包含隐藏评分 |
| `score()` | 选择结束后的离线评估结果；评估不可用返回 `None`，不能用零伪装评估完成 |

核心只需要一个提供原生文件面定义的轻量 substrate 对象和对应编辑提示注册；实际运行由适配器负责。无需实现所有执行器协议，也不修改上游递归算法。[H1、H2、H6]

在本步启动时，为固定版本 `prompts._SURFACE_TEXTS` 注册 `native`，提供自定义 `surface_md/inv/dom/tts_surface`，完整替换不适用的工具、脚本、hook 和按需加载指引。首轮固定 `BenchPrompts.prompt_pack="adapt"`，拒绝 tts，其 `_TTS_INV` 等模板不会随注册条目自动适配。私有注册表/类型需锁版本并做无模型兼容检查；上游通用树仍识别脚本路径，因此 `validate_tree()` 必须复用 B 的白名单与实际可消费性检查。[H6、H7]

基线 `systemprompt.md` 预先点名三角色 skill，保证 frontmatter 一致。新增 skill 的触发行写入同一可编辑文件，`SurfaceSpec.autotrigger_file` 指向 `systemprompt.md`，不写冻结 guardrails；阶段只有两次尝试，不能把因文件面冲突导致的回退误判成策略无效。[H7、H8]

把 B 的冻结规则只读说明复制到 `task_files` 对应的 `source/frozen_rules.md`，在 `BenchPrompts.yardstick/domain_guidance` 给出摘要和定位。可见字段会对 benchmark/evaluation/grader/rubric/score 做英文子串拒绝，接线前检查文本；只描述分析工作，不把隐藏答案、评分或标签混进规则。[H1]

模型通道另行验证：现有分析模型仍通过本项目 PydanticAI/API 配置运行；harness2 编辑/选择通道使用其支持的 `opencode` 或 `claude_cli`。前者要求带 provider 前缀的模型 ID。不能假定当前 `config.yaml` 会被优化器自动复用。[H1]

安全边界与最小试点一起做：仅导出静态文本；编辑器只写候选 harness；分析执行器只读材料、只写自己的结果；首轮禁用可执行脚本/plugin。优化器工作区排除 `.env`、`example3标准答案.md`、人工比较、家族标签和 grader 输出。`leak_globs` 是补充，白名单与文件权限才界定实际可见材料。限制不必要网络访问，同时保留必要的模型服务通道；不能把“彻底断网”与远程 API 调用混为一谈。[H5]

验收：用无付费调用的执行替身检查基线、INV、DOM、合成、两层门槛、轨迹、失败和恢复。`execute(None)` 与显式基线必须经过相同加载器、Workflow、指标和输出路径；提示允许路径与真实装载一致；运行身份不符不能复用缓存。B/C/D 共享文件整合后在目标培养环境通过此检查，才进入 E-2。

### E-2. 诊断后选子图，再校准与试点

1. 冻结 E-1 验证过的运行环境、执行版本、基础 harness、模型/预算、指标和整样本输入。用这一新路径运行一次带完整轨迹的整样本，生成问题索引；这是诊断，不是波动校准或改进证据。
2. 将问题对应到原始材料、实际 prompt、上游摘要、Reviewer/修订记录及全材料审计，按 G 分类。选择影响关键结论、确有策略改进空间的目标包，再取全部祖先形成闭合子图；冻结任务范围和主要验收事实。J04 仅保留为闭包格式案例，不默认是首个试点。如果已确认主要阻碍需要先补能力，可直接触发 G，省去没有有效干预点的递归。
3. 对该固定子图、同一基础 harness 独立运行 **3 次基线校准**。由 D 统一计算行为/引用总数、失效引用数及比例、缺有效引用的 confirmed、重大复核问题、修订拒绝、token 和耗时；保存原始记录。固定温度不能代替重复测量，三次极差/中位数只用于噪声初筛，不是可靠置信区间。
4. 保持相同条件跑 `parallel, k=1`，若得到流程完整的最终候选，再对该候选补 2 次独立执行，使其也有 3 次观察。k=1 仍没有质量选择模型，结果进入 G 作外层比较。

外层校准不会自动成为 harness2 的基线集合：k=1 内部仍产生一个 base。按此方案，首轮预算包含 **1 次整样本诊断＋3 次子图校准＋4 次递归内子图执行＋2 次候选子图复验**，即一次整样本加九次子图执行，另加编辑/合成/反思；缺候选、修复与失败重试需分别记录，发布的整样本重复测试另计。这不是十次 LLM 请求，也不能按包数推算省费比例。

基线只在**同一实验版本和任务范围**内复用。改变材料、闭包、实际指令、模型、预算、执行能力、冻结规则、关键依赖或指标口径后，必须登记新实验版本并重测受影响基线。若只是指标实现变化且保留了足够的原始材料/输出，可以同时重算基线与候选；无法完整重算则重跑。不能把子图的波动范围用于整样本，也不能用旧能力版本的基线比较新能力候选。

### G. 依据原因和收益决定下一步

**先分清问题来自哪里，再判断是否值得继续递归。** 当前流程只按固定 A/R/R 节点调用；`max_model_requests` 默认 3、配置上限 10，并不是写死只能填 3，但单纯调大数字不会产生工具循环或跨包语义分析能力。[E2、E7]

| 问题来源 | 需要的证据 | 处置 |
|---|---|---|
| 策略可修 | 必需材料确实进入当前角色上下文，仍漏查、条件/数据去向写错、证据分级不当 | 保持执行器不变，在 B 开放的策略范围内优化 |
| 装载/交接或程序契约缺陷 | 材料已提供但未送达所需角色、提示/作用域与实际材料冲突，或审计/文件面本身有误 | 先修最小程序缺陷；不让改进模型用策略绕过；相关版本重新验证 |
| 输入或能力不足 | 全材料核对后仍缺关键来源，或需要当前没有的读取/工具/跨包语义节点 | 先补导出输入或第 4 节所需能力，再回 E-1/E-2 |
| 原因或收益不确定 | 单次差异、日志不足、多个改动混杂、观测落在波动内 | 记录证据不足，限预算补一次有明确问题的诊断或重复；不能自动归为“需要工具” |

单包 `not_in_current_packet` 是延后核查标记，不等于全样本缺材料；无效函数/行号也可能是引用写错或范围错，必须对照原始材料和全材料审计。不能由“失效引用多”直接推出应建补料工具。[E13]

决策不按条目数量简单多数票：一个阻断核心结论的能力缺口，可能比很多 minor 策略问题更重要。预先固定关键问题的严重程度、事实保留、质量容差与成本预算。策略干预确有重复收益、关键指标不退步时，进入更多独立训练任务并积累 F 的证据；确认能力阻断时，提前最小能力扩展。没有超出噪声的收益时先判证据不足或停止当前递归方向，不能直接宣称策略无效，也不能无依据扩大功能范围。

能力扩展不必拆掉已经接好的 harness2 适配层。保留加载/日志/指标接口，更新实际支持的策略与文件面，重走替身检查并建立新基线，再继续试点。

### F. 建立对照评估与发布流程

样本准备已从步骤 0 并行推进，到本步接收实际就绪的独立训练任务和留出任务。当前目录可确认的单样本夹具只适合接线与回归，不代表其他目录没有样本；未取得新输入时，可以完成接口和单样本试点，但不能声称完成跨任务发布。多个同源子图可在训练任务流内交流经验，这不等于独立样本的迁移证据，也不保证准备线一定按时完成。

比较同输入、同预算的基线与候选：核心行为精度/召回、关键条件与数据去向正确性、IOC 精度、失效引用率、未获证据支持的确认结论、丢失结论、请求/token/时间/成本。ATT&CK 映射仅在交付要求包含它并有标注时加入，不能当成当前已实现能力。

重复比较使用 E-2 同版本任务的基线与 G 的预设关键指标容差；仅有一次较好或落在基线波动内时记为“证据不足”，不宣布提升。三次运行只提供初步区间，样本少、变化混杂或结果边界接近时，应扩大复验，不能把极差当显著性检验。发布涉及整样本任务时，另做同版本整样本基线与候选重复验证；不同子图的原始数量不可直接横比，同源子图多次 helped 不算跨样本收益。

**harness2 的内部候选选择不承担本项目的上线批准。** 对单任务改进做离线分析后，必须冻结候选，在没有再针对该留出样本编辑 harness 的条件下测试迁移效果。候选不能仅因同一道题得分更高就成为下一版基线。`score()` 保持在选择后调用；独立发布流程使用这些结果作采用/拒绝决定，不能把标准答案回灌给递归编辑器。[H1、H3]

**补齐跨任务合并，明确发布候选的来源。** 上游每个新任务都重新读取 `base_harness()`，经验库只是改进参考，不会使下一任务继承上一任务的 harness。单任务采纳结果先进入待审区，不能默认就是待发布版本。[H10]

首轮由人定期合并，按以下顺序推进：

1. 积累多个独立样本的任务记录，以 cue/lesson/evidence、改动 diff、事件定位、编辑判定和重复执行事实为依据。不能只拼接整份单任务 harness，也不能把模型写的 helped 当作已证实的因果关系。
2. 只将跨多个独立任务重复显示收益、无未解释 hurt、且非 confounded 的改动列入合并；优先处理 INV 通用策略，DOM 按预定义领域保留。单样本专用结论和事实不进入通用策略；有潜力但证据不足的改动继续待审。
3. 从固定的已发布基线构建一个新的**合并候选版本**，逐条记录来源任务、适用域、取舍与冲突处理。合并步骤有自己的版本号、记录与成本；若以后由有上限的模型会话辅助，也必须与单任务递归分开记账，且看不到隐藏标签/评分。
4. 合并候选冻结后，先回归训练任务，再在未参与编辑的留出样本上运行整样本测试与必要重复比较；合并后的相互作用可能使原有收益消失，不能省略重测。其关键质量指标不差于基线、具有可重复收益，且通过分析师审核后，才发布为不可变版本并保留上一版回滚。

经验至少保留 cue/lesson/evidence、适用域、来源任务和运行、重复测量、验证状态。人工审核的是候选版本，正常分析无需逐次审批。整个流程为“单任务记录 → 跨任务合并候选 → 回归与留出验证 → 审核发布”，与 harness2 内部的采纳区分。

上岗时直接加载已发布 harness，默认不递归。待审经验库供离线编辑使用；已审核经验若确需线上检索，再实现明确的读取方式。不要让生产分析读取持续变化的训练运行库，也不要仅靠固定 tag 共享生产经验。[H4]

## 4. 条件能力扩展：由 G 决定是否提前

只有已确认的输入/能力瓶颈才调整先后；不预设必须等全部培养闭环结束，也不因一次没有测到收益就启动工具建设。若只是导出材料不足，先补输入；若材料已在当前导出中但未送达角色，先修装载/交接；确实需要主动获取或新的跨包语义节点，再实施下面的能力。保留现有适配基础，变更后回 E-1/E-2，不复用旧比较口径。

**主动补料**：先用当前导出材料建立只读 `get_function/search/callers/callees` 等必要接口；若必须连接上游 SQLite，只定义并验证只读数据契约，不改第一、第二阶段内部流程。当前材料索引仅检查存在性，`material_needs` 不会自动取回材料。[E6]

这一步还要同时解决三个问题：取回内容进入本次材料快照并被引用审计索引；Worker 的可用材料边界随工具返回明确更新；工具调用使用独立上限并为 Reviewer/Reviser 保留预算。当前 A/R/R 默认预算为 3 次核心模型请求，调高上限本身不能增加工具能力，不能直接放进任意次数的工具循环。[E2、E7]

**跨包语义复核**：若目标包含还原全局行为链，应在全包结果可用后单独设计有界分析节点，让它能读取原始材料、识别跨包条件/数据流并提交可审计事实。现有全局节点只决定已有事实的 ID 关系，没有这项职责；简单恢复旧配置或要求报告模型“再想一遍”都不能补齐契约。[E2、E9]

以上两项会扩大 harness2 可以优化的空间。执行器权限、证据规则与预算先由项目明确，再逐步开放策略，避免把框架建设交给递归模型自行决定。

# Content Studio 文章与当前 src 的对照分析

结论：当前项目已经具备清晰的领域 harness：程序控制流程、预算、事实来源和修订权限，模型负责分析、关系判断和报告组织。最值得借鉴的是让专家反馈形成可验证的改进循环，并把审计结果落实为交付门槛。

## 分析范围与依据

- 分析日期：2026-10-28，以当前工作区源码为准。工作区原本存在大量未提交修改。
- 用户提供的 [AIHOT 页面](https://aihot.news/items/l63udrrcunv0qy04ve4s71g02) 及其指向的 [LangChain 官方原文：How We Built Our Design Agent](https://www.langchain.com/blog/design-agent)。官方页面标注 2026-10-27。
- 本次读取主要编排、执行器、角色与技能、证据校验、全局整合、报告及相关测试，执行离线回归与四项合成探针。
- 本次不修改业务源码，不调用外部模型，不执行恶意样本。以下建议均未实施，也没有进行真实模型质量或成本对比实验。

## 当前实现的实际形态

主路径：材料包与依赖清单 → DAG 调度 → Analyzer → Reviewer → 条件 Reviser → 程序精确归并 → 模型关系决策 → 程序组装 canonical facts → 三层知识报告 → 可选 HTML 报告编排与渲染。

| 位置 | 已实现的职责 | 对分析结论的意义 |
| --- | --- | --- |
| `orchestration/batch.py`、`dag.py` | 依赖满足后调度、分支并发、失败依赖交接、紧凑事实投影 | 已有异步执行和包间边界；运行状态主要在当前进程内维护 |
| `workflow.py` | 固定 A/R/R 流程、修订条件、共享预算、降级保全 | 流程由程序控制，Reviewer 失败仍能保存 Analyzer 结果 |
| `execution/stage_runner.py` | 流式捕获、结构化校验、格式修复、原始及部分结果保存 | 格式失败不会直接抹掉所有分析；必需字段缺失时停止格式修复 |
| `harness/loader.py`、`harnesses/baseline-v1/` | 角色技能展开、可信规则组合、不可变指令及指纹快照 | 已可追溯实际使用的分析规则；目前是按角色确定性加载 |
| `investigation/revision.py` | 生成允许修改范围、程序合并、保留未授权字段、重检结果 | 修订权限有程序约束；核心 Reviser 仍返回完整结果 |
| `reconciliation.py` | 精确归并、只让模型做 ID 关系决策、来源及覆盖检查 | 事实全文由程序从原结果组装，减少全局改写造成的丢失 |
| `evidence/` | 材料清单、范围、引用位置与原文片段 | 已有提供分析工具所需的索引基础；位置存在性不证明语义正确 |
| `reporting/` | 知识分层、报告正文引用、一次局部补丁、模板渲染与诊断 | 报告内容可编辑且可重放；合同校验不能替代专业判断 |

这是一个有界分析流水线。`execution/llm.py:108` 的 Agent 构造没有注册主动读取材料等业务工具；`output_mode=tool` 用于结构化结果输出。它与文章中的通用计算机环境在任务范围上不同。

## 可以直接借鉴的做法

以下是结合原文方法与当前代码作出的判断和建议。

### 1. 把“正确”和“专业”分别建设

文章把可测量问题交给程序检查，把专业判断及反馈理由放进技能。当前项目已有相同基础：引用检查负责函数和行段存在性，`control-flow-conditions` 技能解释如何判断真实门控条件，`packet-fact-boundary` 技能解释跨包审阅边界。

应继续用“判断原则 + 正反案例 + 为什么”的方式建设技能。例如：调用后的返回值检查不能反向约束调用是否发生；上游已报告的行为不因本包未重复而成为漏报；读取来源文件与感染 IOC 具有不同含义。

`reporting/composition.py:246` 明确只收集确定性合同错误，不保证正文真实。当前行为覆盖主要根据合法引用是否进入正文内容块统计，仍需用专家标注案例检查条件、因果及确定程度是否被准确表达。

### 2. 把审计接到交付决策上

这是当前最应优先落实的一点。

**缺少源码时，未核验可能表现为完成。** `reporting/knowledge_report.py:194–209` 在没有源码时设置 `status=not_run`、`passed=True`；后续问题收集跳过此状态，报告可被标为 `complete`。本次用一条引用不存在函数的 confirmed claim 复现了这一结果。

**来源审计失败与生成文件是两件事。** `save_knowledge_outputs()` 仍写出 `_final_report.md`，其中包含完整性警告，结构化状态为 `incomplete_provenance`。`reporting/service.py` 会返回 `completed=False`，但 `cli.py:103` 没有据此决定退出状态。

**HTML 当前明确属于预览。** `reporting/html_report.py:241–247` 保存 `source_audit`，没有将该审计作为阻断条件。本次使用现有测试的固定响应，复现了 `source_audit.passed=False`、`status=completed`、`preview_only=True` 且 HTML 存在。不能将该 completed 解读为来源已核验。

建议保留诊断、草稿及降级结果，同时明确区分执行完成、证据核验和可交付状态。证据核验使用通过、失败、未运行三种状态；正式交付要求关键检查实际运行且通过。跨包引用仍可在单包阶段暂缓，留到完整材料阶段统一核对，避免破坏现有降级处理能力。

### 3. 交接必须保留限制和质量状态

`orchestration/dag.py:113–165` 输出行为、证据等级、条件、数据流和引用，但不输出 claim 的 `limitations`，也不传递封套中的 `review_completed`、`revision_failed`。`workflow.py:348` 允许评审失败后保留分析结果并返回 success，因此 success 不能说明评审已完成。

本次构造了一条带明确限制的 suspected claim，并设置 `review_completed=False`、`revision_failed=True`。下游文本包含 suspected 和 success，但上述限制和两项质量状态均消失，甚至可以显示 `unresolved: none`。

最小改进是在现有交接投影里补入这些状态和会影响结论的限制，保持原有依赖调度与失败保全方式。结构化校验通过、引用位置有效、结论获得语义支持，应在使用上区分清楚。

### 4. 从“保存评审”走向“积累可验证经验”

当前已经保存 Reviewer 输出、修订范围、原始响应、格式错误与 harness 快照，但 `src` 尚未实现文章所述的经验提取、后续任务评价及晋升到技能的学习循环。

最简单的起点是利用已有结果记录人工确认的纠错案例：原结论、问题、证据、正确结论、理由、适用条件、关联技能与 harness 指纹。自动 Reviewer 的意见需要验证，不能直接当作知识来源。

先把真实失败整理为回归案例，再将多案例验证有效的通用原则写入版本化技能。样本自己的路径、域名、行为和归因继续属于案件事实，避免成为其他样本的默认知识。团队证据标准与报告偏好也应分开管理。

### 5. 用评测决定提示词如何简化

文章描述了模型进步后删除补偿性规则的经验。对本项目，应该结合 `harness_snapshot.json` 比较不同模型及规则版本，保持输入、结果合同和程序门槛一致。

建议从现有标准答案与冻结案例构建一个小型评测集，按样本划分规则开发案例和未见测试案例。首先记录无依据确认、核心行为遗漏、条件错误、错误 IOC、修订丢失事实，以及请求数、tokens、可用成本和耗时。语义指标需要人工标注或复核；现有单元测试通过不代表这些指标已经达标。

通过这样的对照，才能判断哪些重复或补偿性提示可以删除。来源追溯、修订权限、预算与不凭空补造事实等程序约束有独立的正确性作用，应持续保留。

### 6. 在已具备的结构上增加工具与恢复能力

文章强调为专业任务提供合适环境。当前 `evidence/inventory.py` 与 `snippets.py` 已有材料和函数行段索引；如果后续证实大材料输入成为瓶颈，可先提供受材料范围约束的只读函数检索和片段读取，记录访问来源并共享预算。当前只有两个分析技能，按角色加载仍是简单合理的方案。

调度方面，`batch.py` 已经使用异步任务和并发限制；`replay.py` 能复用保存的 Worker 结果做全局整合。尚缺的是按 job 或阶段恢复正在进行的批次，以及运行中接受新反馈的协调层。若长时间批次成为实际需求，可先按材料、依赖、harness 和配置指纹复用已完成 job，再考虑交互式任务管理。

报告方面，`reporting/agent.py:185–201` 已采用局部补丁、程序合并和完整复检，是可继续沿用的设计。人工反馈也可绑定具体事实与章节，减少整份重写。以上工具与恢复改进应由实际瓶颈触发。

## 建议实施顺序

1. **先落实证据交付门槛，并补全交接状态。** 验收重点是未核验不能表现为核验通过、来源失败不能成为正式交付、限制和评审状态可以追溯。
2. **建立小型真实案例评测集和人工确认的反馈记录。** 利用现有阶段产物与指纹，衡量每次技能、提示词和模型修改的影响。
3. **根据评测与运行数据改善上下文和恢复。** 再决定是否需要按需读取材料、扩展技能路由或按 job 恢复。

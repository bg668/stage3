# 当前项目的 harness 迭代优先级

最新代码/产物核实补充：用户进一步说明人工材料实验源于自动筛选后的规模与优先级问题。`reference` 样本3保存记录显示两阶段保留100/500个函数，却仍保留52.9%的代码字符；旧事实准备选中32个函数后，10个完成抽取、2个完成审阅，因输出预算停止，并有审阅超时/协议错误和汇总上下文超限。人工16包包含123个不同函数，不能将其优势只解释为数量缩减。当前应并行区分“固定人工材料下的局部分析能力”与“自动候选在固定预算下的选择组织能力”；详见 [reference 定量分析](reference-triage-resource-analysis.md)。这些历史执行器产物不等同于当前 A/R/R 的运行效果。

2026-10-30，按最新背景修正：第一、二阶段筛选更可能与恶意判定、检测、关联溯源有关的函数，作为调查线索入口。实际执行发现阶段三效果不佳，因此当前阶段三有意使用人工提取、确认后的函数材料包，以减少上游筛选等外部因素，验证理想输入下的分析效果。已有 3 个案例应先在这种受控条件下诊断和改进阶段三。上游连接安排在阶段三达到可接受效果之后。

本说明基于当前工作区源码、已有真实输出夹具和本次离线探针。它是实施建议；本次没有修改业务源码、接入优化器或调用项目分析模型。

## 当前背景与实验边界

以下业务背景来自用户澄清：

- 阶段一、二的目标是提高与三个业务目标相关的函数被发现的概率，输出线索入口。
- 当前 `src` 对应阶段三，实际使用中效果尚不理想。
- 当前人工提取和确认的材料包，是为了控制输入因素而有意设置的理想输入，并非亟待替换的临时接入方式。
- 已有 3 个案例，下一步先使用这 3 例，不以扩大案例数量为启动条件。

这使前一轮“优先贯通上游并做三例全流程基线”的建议失去适用前提。当前首个里程碑改为：在固定人工材料下定位阶段三瓶颈，验证阶段三能否产生可接受的分析结果。人工确认材料的选择，不自动证明其中所有语义关系、数据或外部归因已经闭合；实际不足仍应记录为限制。

### 第一个里程碑：理想输入下的阶段三能力基线

当前路径：固定的人工函数材料包及依赖上下文 → Analyzer → Reviewer → 条件 Reviser → 全局事实整合 → 报告 → 人工逐项复核。

| 顺序 | 具体任务 | 目的及完成标志 |
| --- | --- | --- |
| 1 | 冻结 3 例人工材料、分包、依赖上下文与当前策略版本 | 排除选料变化及多个变量同时变化，保证前后比较可解释 |
| 2 | 为每例列简明预期检查点 | 覆盖恶意行为与条件、检测价值、关联溯源线索及其证据边界；结果可逐项判断 |
| 3 | 在同一模型、预算和程序基线上运行阶段三 | 保存每阶段输出、修订差异、全局结果和报告，形成 3 份阶段三基线记录 |
| 4 | 沿处理链追踪每个错误第一次出现的位置 | 确定是初步分析、审阅、修订、交接/整合还是报告环节引入或未纠正 |
| 5 | 修正一个主要问题，再用相同材料比较 | 用事实检查点衡量改善与退步，同时保留正确案例作为保护 |

当前第三阶段入口是 `orchestration/batch.py`；`io.read_packet()` 读取材料；`orchestration/dag.py` 安排任务和交接；`workflow.py` 编排 A/R/R；`reconciliation.py` 整合事实；`reporting/` 编排和呈现报告。它们构成本轮诊断范围。

逐阶段检查以下典型情况：

- Analyzer 是否在材料已支持的情况下漏行为、写错条件或数据流，是否产生无依据的强结论。
- Reviewer 是否漏检真实错误，或提出错误纠正、扩大审阅范围。
- Reviser 是否落实正确修订、保留其他正确事实；程序合并是否按预期生效。
- DAG 交接与全局整合是否丢失限制、上下文或事实关系，是否产生不当合并。
- 报告是否准确表达已有结论、检测信息和关联线索，并保留必要的不确定性。

每个问题记录原始材料、首次出错阶段、错误判断、正确判断、证据和修正理由。案例不只看报告能否生成，而要核对给定材料中应当得到的事实是否得到正确处理。

### 三个业务目标分别检查什么

| 目标 | 在当前理想输入实验中核对 |
| --- | --- |
| 恶意判定 | 核心行为、触发条件、数据流及证据能否支持判断，确定程度是否恰当 |
| 检测 | 能否提取有检测价值的对象和行为特征，区分普通读取对象、环境探测与特异指标 |
| 关联溯源 | 能否提取材料支持的可比较特征和线索，说明关联依据与限制，避免无证据归因 |

上述检查点是本轮验收口径建议，并不要求每个样本同时具备所有类型的事实。人工材料未包含必要信息时记录缺口；人工确认的入口不能替代支持具体结论的证据。

### harness2 和上游连接安排在何时

在 3 例基线能逐项判断之后，程序性缺陷由代码修复；仍复现的分析策略问题可进入 harness2 受限优化。先选择一类主要问题，固定材料与程序，用角色/技能候选做对照，再保存有效经验。不同阶段改变要分别留版本，避免同时改变选料与分析策略。

阶段三在人工确认材料下达到可接受效果后，再将阶段一、二的真实筛选结果接入。此时分别比较人工材料与自动材料下的结果，识别上游召回/选料损失及其对三个业务目标的影响。上游连接是后续集成任务，不作为当前能力验证的前置条件。

3 例可用于首轮诊断和初步对照。若某例已反复用于改进，不再将其描述为未见留出样本；后续需要独立泛化判断时，再准备相应材料。

第一轮预期交付：3 份理想输入下的阶段三基线、3 份业务检查表、按首次出错环节归因的问题清单，以及一轮单点修改的前后对照。下文评价、学习和发布机制用于支持这一目标，具体工作量随首轮发现确定。

## 0：先让优化实验的判定可信

本次重新复现两个具体问题：

1. `reporting/knowledge_report.py:194` 在无源码时返回引用审计 `not_run/passed=true`，知识审计可能通过，报告状态可能为 `complete`。实验应将核验状态分为已通过、已失败、未运行。缺少核验条件时记录实验不可充分评价的原因，不把它隐藏在通过率中。
2. `orchestration/dag.py:113` 传递行为和证据等级，但遗漏 `limitations`、`review_completed`、`revision_failed`。本次带限制及评审失败状态的合成输入，在交接中只保留了 suspected。这类上下文损失应通过程序投影修正，再冻结实验基线。

2026-10-29 的 HTML 改动已经增加 `_audit_meta()`，使未知或未运行状态显示为未审计。本次核对了当前源码；这里的建议针对底层统一判定与优化实验资格，不重复声称当前 HTML 会将未运行展示为通过。

执行状态、程序合同校验和专业分析质量分别记录。格式修复失败应保留诊断；引用位置有效仍需要判断观察描述和条件关系是否正确；代码修订已被程序接受仍需核实语义。

这一步的作用是消除可确定的工程干扰。它可以独立修复和验收，后续实验统一使用修正后的程序版本。

## 1：先沉淀专家能确认的案例

首批不追求大型知识库。先整理一批可以逐条复核的案例，覆盖核心行为、触发条件、数据去向、IOC 角色和调查边界等已有问题，同时保留正确案例以检查过度纠正。

一条案例至少保留：

- 样本、材料包和相关依赖上下文，定位到本轮可见源码。
- 原判断、评审意见、实际修订，以及原始输出与程序合并结果的区别。
- 预期事实、禁止作出的强结论，以及允许保留的不确定性。
- 支持纠错的函数和行段、修正理由、适用条件及反例。
- 专家确认状态、来源记录和使用的模型/harness 版本。

例如“把调用后的成功判断写成调用发生的先决条件”，可提炼为控制流核对原则。但历史错误需要先在当前版本诊断；现有 `control-flow-conditions` 已增加相应指导，不能预设错误今天仍会重复。

`revision_20261021` 中还区分了真实输出与整理后的协议输入，这个来源边界应继续保留。自动 Reviewer 的意见先作为候选反馈；与程序允许的修订一起通过专业确认后，再作为可复用经验。

这些记录同时服务两个用途：向优化器解释失败原因，以及向验收器说明正确行为。二者的数据使用范围应分开，留出验收材料和标准不进入优化上下文。

## 2：用业务质量建立最小 evaluation

第一版评价应包含两组结果：

| 评价 | 示例 | 如何使用 |
| --- | --- | --- |
| 程序约束 | 结果可解析、引用核验已执行、来源可追溯、没有丢失原有正确条目或越权修改 | 决定是否满足采用条件，失败不能用其他分数抵消 |
| 分析质量 | 核心行为遗漏、错误确认、条件错误、数据去向错误、错误 IOC、限制表达是否准确 | 按案例的事实检查点和专家判断比较基线/候选 |

此外记录请求数、输入/输出 tokens、格式修复量、耗时和可获得的成本。减少结论、全部降为线索可以降低错误确认，却可能增加漏报，因此需要同时检查核心覆盖和确定程度是否恰当。

先从当前版本重复少量基线执行，观察结果波动，再确定候选改善门槛。固定任务不代表模型输出固定；随机种子也不能被当作模型采样完全可复现的保证。

样本划分以独立样本为单位。同一样本的不同材料包可以用于功能诊断，但不能据此宣称跨样本泛化。需要保存正常与失败数量、未评分原因，以及任务级对照，避免仅展示成功运行。

## 3：用 harness2 验证一个受限的改进问题

适配器连接现有 Workflow，并把候选编辑转换成当前 loader 真正消费的角色/技能文件。接口联调首先证明“修改确实进入了本次实际指令和快照”，然后验证执行失败、预算终止和产物保留。

首轮仅开放受控的角色说明及分析技能。固定程序、schema、来源规则、修订权限、材料、模型与预算，避免多个变量一起变化。现有 loader 只接受指定文件结构，不能将优化器生成但项目不会读取的文件算作有效改进。

首个诊断主题建议使用已有控制流条件案例。当前基线确认还有可复现问题后，再让 harness2 比较候选指导。若诊断显示问题来自材料缺失、上下文丢失或执行能力不足，则将其归入相应工程工作，重建基线后再实验。

harness2 的 Propose–Probe–Compose 结果可以作为待采用候选；是否发布仍由本项目在独立任务上的验收决定。项目旧评估固定 `bg668/harness2@1cfe254`，正式适配前要锁定并核对官方实现版本，不直接沿用旧接口结论。

## 4：把结果沉淀到实际会被使用的位置

LangChain 的快速反馈与慢速积累可映射为：

- 快速记录：每次人工纠错、失败或有效修订后，关联已有阶段产物，保留证据、理由和适用条件。
- 验证后沉淀：把经多个案例支持的方法写入版本化角色/技能，在留出任务上复验，并保存采用或拒绝的原因。

第一版采用离线提炼和明确的版本发布。当前 loader 已支持新目录和快照，可直接复用。只记录被当前版本实际消费的规则；避免将大量未经验证的经验全部追加到每次提示词。

样本行为、对象及归因仍保留为案件知识；通用控制流方法、审阅方法与错误模式进入角色技能。跨样本事实检索可在上述质量闭环稳定后建设，并使用独立参考上下文；当前首先建设方法与案例的积累。

# reference 代码与产物：筛选规模、优先级和阶段三资源分析

## 结论与证据范围

现有证据支持用户指出的容量矛盾：前两阶段完成了“值得继续调查”的筛选，但未把调查范围转成符合资源预算、围绕业务目标安排的工作队列。历史阶段三还有输出膨胀、审阅失败和汇总上下文超限的问题。因此，应分开验证输入选择/组织、单任务产出效率及预算内的目标覆盖。

本次只读取代码、JSON/JSONL 与 SQLite，不执行样本、不调用分析模型、不重跑前两阶段。3 个 SQLite 分别包含 393、140、500 个函数。本目录只提供 `examples/out/debug_03` 一组处理输出，下面的筛选率和资源统计仅适用于样本 3。样本 3 数据库 SHA-256 与 preprocess.json 中记录相同。

`reference/src` 提供 preprocess、triage 的实现；旧 stage3 只有产物，没有相应规划/事实准备执行器源码。当前项目 `src/bounded_investigator` 是另一套 A/R/R 实现，不能将旧执行器的错误直接归因到当前执行器。

另外，输出记录的初筛模板为 r1.v2/r2.v1；当前参考源码标识为 r1.v3/r2.v2。当前提示词已有更严格的调用上下文要求，不能据旧结果断言现版模型筛选会产生完全相同的决定。

## 2. 为什么筛选后仍然多、优先级仍不够用

### 第一阶段：规则优先级决定分类，不决定调查收益

`preprocess/rules/__init__.py:38` 的顺序是规则匹配优先级；`rule_engine.py` 按 first-match 决定分类。它没有在保留函数之间建立“应先分析谁”的队列。

`r102_dangerous_api.py` 在至少命中一个危险 API 时返回 PROGRAM_ANALYZE。本例 42 个函数由此直接保留。`triage/input.py:72` 仅把 UNDECIDED 交给第二阶段，因而这些直接保留函数不会再由第二阶段比较调查价值。它们可能值得保留，但危险 API 的存在不能直接给出目标贡献、上下文成本或调查顺序。

本例库函数规则命中为 0，材料还记录了 FLIRT 匹配不足的提示。可以确认自动库排除在本例没有贡献；不能仅凭该指标判定哪些函数实际上是通用库函数或应删除。

### 第二阶段：生成保留集合，没有预算内排序合同

`triage/domain.py:115` 的 FunctionVerdict 和 `:156` 的 FinalVerdict 主要字段是 decision、reason、短 note、来源轮次及失败标记，没有三个业务目标的贡献、预估成本、边际覆盖收益等排序信息。

本例 57 个模型保留项的 reason 为 linking 17、collection 12、anti-analysis 12、host-interaction 6、data-manipulation 5、load-code 3、persistence 2。这是调查类别，不足以区分同类函数中谁能最先闭合一个关键问题。

`final_verdict.py:25` 按预处理顺序归并；第一、二轮提示词的任务是判断是否值得精读，第二轮信息不足时保守 ANALYZE。技术失败也有保守保留路径，但本例 forced_analyze=0，第一、二轮执行均无终止失败，不能把本次 100 个保留函数归因于失败回退。

本次第二轮补料 26 包中有 11 包 PARTIAL、4 包 truncated。补料不足会限制判断，但这几个集合可能重叠，也不能据此判定对应保留项都是误保留。

第二阶段已有成本：43 次记账请求、177896 输入 tokens、15689 输出 tokens、wall_ms=764039，约 12.7 分钟。`triage/contract.py:56` 把 est_cost 固定写成 0.0，因此它不是实际免费或已结算金额。

## 3. 旧规划器已经有压缩，不能忽略

`stage3/investigation_plan.json` 记录 planner_version=stage3-planner-v4：

- 95 个上游主体候选，分成 19 owner、65 context、11 outside/deferred。
- 17 个行为区域，18 个调查任务；100 个保留函数中的 5 个转发支持不在这 95 个主体候选内。
- primary 与 support 合计出现 209 次，涉及 125 个不同函数。原始 100 个保留集合之外的函数可作为上下文补充。
- 支持函数 F-0495 出现于 6 个任务，F-0496、F-0375 各出现于 5 个任务。这是规划引用重复，不足以证明实际重复付费读取；后续 function_fact_plan 已有共享 job 和任务需求映射。
- I-0018/F-0500 横跨 5 个行为区域，被标为 semantic_overloaded；support=32，另有 39 个 behavior context 被剪除。任务数或主函数数低，仍可能存在语义负荷与上下文问题。

这些结果说明旧流程已经尝试行为分区、主体/支持分工和共享事实，下一步应检查这些机制的实际效果。任务文件没有显式 priority 字段，但有 sequence；缺少对应规划器源码，不能断言 sequence 的具体算法。

## 4. 历史失败证据：输出预算、审阅和汇总共同受限

`stage3/facts_prepare/run_state.json` 与调用日志记录：

| 项目 | 实际记录 |
| --- | --- |
| 选中函数 | 32 |
| 已抽取函数 | 10 |
| 完成语义审阅 | 2；另有 8 个 PENDING |
| 未完成总量 | 状态文件 completed=2、partial=8、failed=22；failed 不应全部解释为模型技术错误 |
| 累计输入/输出 | 57186 / 60742 tokens |
| 输出总预算 | 60000 tokens |
| 停止原因 | AGENT_TOTAL_OUTPUT_BUDGET_EXCEEDED，recoverable_stop=true |
| 质量 | NOT_EVALUATED，correct_fact_coverage=null |
| 汇总探针 | CONTEXT_LIMIT；完整事实视图超限，未截断、未调用汇总模型 |

JSONL 共 22 条调用记录：规划 2、函数抽取 10、语义审阅 10；runtime 的请求记账字段为 20，不能混为同一个计数口径。

按日志逐条累加输出 tokens：规划 2297、抽取 40925、审阅 17520，总计 60742。抽取 10 个函数平均约 4092.5 输出 tokens；这个样本的主要显式 token 压力发生在产出侧。

10 次审阅记录：2 REVIEWED、8 PENDING。PENDING 包括 5 次 60 秒超时、2 次 KeyError（S1、INVALID-0），以及 1 次预算停止。存在技术/协议问题，不能把未完成全部归为需要更多算力，或全部归为恶意代码推理能力不足。

`agent_runtime_manifest.json` 记录审阅 output_tokens=2000，但已记录的审阅响应中包含 4771、8039、3010 等输出 tokens。配置值与日志值存在差异；旧执行器和供应商适配源码未提供，不能直接判定参数未传、模型忽略、统计包含何种 token 或具体责任。应核对真实请求和计量口径。

### 不能说完全没有优先级

fact_preparation_plan.json 已有 46 张问题卡，26 张 BLOCKING、20 张 IMPORTANT。40 张 rank=50，其余 6 张有不同 rank；最终选中 32 个函数，首项选择理由包含 THEME_ROOT。

因此已有主题优先和优先级标签，但这些标签是否可靠、是否考虑成本、是否能在预算耗尽前得到足够有效结论，目前没有质量评测证据。应评价“预算内闭合多少关键问题”，而非只看 BLOCKING 或选中函数数。

## 5. 人工材料实验实际改变了什么

`examples/input/example3_16_test_packets/README.md` 明确其目标是测试材料充分、问题有边界时的局部分析能力。16 个包包含 124 次函数标题、123 个不同函数，全文字符总数 198060（包含标题和说明，不能直接当作代码字符数与144816比较）。

所以人工实验并非简单把 100 个候选压成少数函数。它同时改变了入口选择、任务分工、相关上下文、问题边界及后续执行合同。当前 A/R/R 又与旧逐函数事实准备实现不同，因此不能把效果差异只归功于筛选数量减少或单一提示词。

人工输入可以继续用于验证当前阶段三的局部分析能力；自动候选实验则用于验证有限资源下的选择与组织能力，两类结果分别记录。

## 6. 当前 src 的对应缺口与建议

当前 `orchestration/dag.py` 的 ManifestJob 定义 job_id、title、depends_on、source_chars、source_count，没有业务优先级和预算价值信息。`orchestration/batch.py:190` 对依赖就绪项按 job_id 排序并排入执行，主要保证依赖与并发，而非按目标收益分配资源。

`workflow.py` 的请求/token/时间限制主要作用于单个材料包，格式修复、全局整合和 HTML 各有独立预算。当前没有样本级、跨任务的统一收益/成本选择和停止策略。单任务有界不意味着整个样本投入可控。

建议下一步分为两项受控实验：

1. 固定现有人工材料，继续验证当前 A/R/R 是否能高质量处理已明确边界的任务，并找出输出长度、修订和报告阶段的实际成本。
2. 用已有自动筛选结果做预算回放：首先为候选补充目标、关键问题、必要上下文、预估输入/输出成本、与已调查区域的重叠；在固定预算下选择少量问题或行为区域，记录已覆盖与暂缓理由。优先证明有收益再扩大执行。

最先增加的位置应在“筛选结果到阶段三任务”的规划边界：`reference` 上游产出保留集合和信号，新的受预算约束的规划产生可追溯任务；当前 `orchestration/` 负责按计划执行和预算状态。不要把危险 API 命中数直接等同于可靠排名，也不要通过任意提高 SKIP 率来满足预算。

当业务目标已达到足够支持时保留尚未分析项及理由；未闭合的关键问题按预期新增信息和成本补料。关联溯源需要的算法、配置或特异特征不能因缺乏危险 API 被机械降级。

harness2 可在评价口径建立后优化角色、调查策略与候选选择，但前提是能观察固定预算内的实际业务产出。当前最有价值的验收指标是：核心结论覆盖、错误确认、有效检测特征、关联线索、单位 token 的有效发现，以及预算内完成率。

## 核对限制

只有样本 3 的保存运行可作上述定量分析；未运行样本 1、2 的筛选。旧执行器缺源码、提示词版本不一致、缺独立人工质量标签，这些限制均保留。本次没有修复代码、重跑模型、执行二进制或验证新调度策略收益。

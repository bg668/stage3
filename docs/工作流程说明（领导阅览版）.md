# 恶意代码静态分析系统工作流程说明

> 本文保留 2026-10-21 的流程快照与当时统计。2026-10-23 代码已按职责重组，当前目录与接口请查阅 [src 架构与处理流程](src-architecture.md) 和 [harness 使用说明](harness-runtime.md)。

**本系统将已准备好的代码材料分批分析，通过“分析—复核—定向修订—全局整合—证据审计”，形成带证据来源和可信程度分层的恶意行为报告、检测线索及补充材料建议。**

适用版本：当前源码 1.7.3。整理日期：2026年10月21日。

## 一、整体工作流程

**材料接入与登记 → 按依赖安排任务 → 逐包分析、复核及必要修订 → 汇总补料需求 → 全局去重与关系整理 → 来源和引用审计 → 输出分层报告。**

这里的“材料包”是预先整理的源码或反编译代码文本；“按依赖安排任务”是指先分析公共基础内容，再将结果摘要交给依赖它的后续任务，无相互依赖的任务可以并行处理。

系统解决三个主要问题：

- **分析规模问题：**将大段材料划为有明确边界的任务，按依赖传递已形成的结果摘要。
- **分析质量问题：**设置独立复核环节，对影响核心判断的问题进行一次定向修订。
- **结果交付问题：**统一整理重复、替代及冲突关系，输出分层结论，并保留证据和处理记录供复查。

## 二、核心功能节点及输出

| 节点 | 核心功能 | 主要输出 | 对管理和交付的价值 |
|---|---|---|---|
| 1. 材料接入与登记 | 读取材料包、任务清单和配置；检查任务是否重复、依赖是否有效、是否存在循环依赖；登记函数、原始行段及附加文件 | 任务依赖关系、输入材料清单、代码位置索引 | 明确本次分析范围，为后续查证和补料提供依据 |
| 2. 依赖调度与结果交接 | 等待上游任务结束后启动下游；按配置限制并发；向下游传递上游结果的紧凑摘要 | 每个任务的执行状态，以及上游行为结论、关键对象、未解决事项摘要 | 让后续分析利用前序成果，控制处理成本 |
| 3. 初步分析（Analyzer） | 阅读当前材料及上游摘要，提取行为、触发条件、数据来源、关键操作和最终去向；标注证据及限制 | 初步分析结果：行为结论、关键对象、证据引用、证据等级、缺口、交接事项、补料需求 | 回答“代码具备什么能力、依据在哪里、还有哪些不确定因素” |
| 4. 证据引用检查 | 用程序检查引用中的函数和行段是否在已提供材料中存在；跨包引用在单包阶段可延期核查 | 引用检查记录；提交复核环节的问题摘要 | 尽早发现位置错误、行段越界等可确定的问题 |
| 5. 分析复核（Reviewer） | 检查影响核心判断的漏报、误判、条件或数据流错误，以及检测指标分类错误；明确修改对象及修正方式 | 复核意见、问题级别、是否需要修订、修正要求和目标对象 | 集中处理会影响结论的问题，避免因一般细节反复返工 |
| 6. 定向修订（Reviser，按需） | 存在重大或严重的包内问题且启用修订时执行；程序只采纳获准范围内的修改，检查结果一致性及新增无效引用 | 修订后单包结果、修改范围及应用审计；失败时保留初稿并记录状态 | 控制修改范围，防止修正一个问题时改坏其他已完成内容 |
| 7. 补料需求核查 | 汇总各包提出的材料需求，对照已登记函数、行段及文件，区分已提供、部分提供、本次输入中未找到、无法判定等情况 | 补料请求清单、材料范围说明，以及后续报告中的材料建议 | 帮助安排下一步取证，区分材料未提供与已提供但未进入分析 |
| 8. 全局事实整合 | 程序先合并完全重复项；模型再判断已有结论应保留、合并、被替代或待决，并处理关键对象的分类冲突；程序组装统一结果 | 全局事实集、结论关系决策、未决冲突、来源映射 | 将分散分析结果整理为统一事实集，并保留原始依据 |
| 9. 全局审计与报告交付 | 核对事实是否来自输入、各来源是否有明确去向；有源码材料时核查全局引用；按证据等级和检测价值生成报告 | 中文报告、结构化结果、来源去向审计、证据引用审计、批次执行汇总 | 让阅读者区分结论等级、审计状态和后续工作需求 |

节点4也会在单包最终结果形成后执行。节点9的全局来源校验和报告阶段的全材料引用检查是不同检查，需分别查看结果。

## 三、每个材料包如何形成结论

每个任务的主要路径为：**初步分析 → 引用检查 → 独立复核 → 必要时修订一次 → 保存最终单包结果。**

复核发现当前包内的重大或严重问题时，才会触发修订。包外待查事项通常登记为缺口、交接事项或补料需求。修订完成后由程序检查并保存，当前流程没有再次调用复核模型的循环。

单包结果主要包括以下内容：

| 内容 | 说明 |
|---|---|
| 行为结论 | 用“触发条件 → 数据来源 → 核心操作 → 数据去向或副作用”描述能力，并保留尚未闭合的关系 |
| 证据及等级 | 标注函数和原始行段，说明该处可见内容；分别记录证据等级与置信度 |
| 关键对象 | 文件、互斥体、注册表项、字符串、网络对象等；同时说明行为角色和检测价值 |
| 缺口与交接 | 记录尚不能判断的问题、原因、影响，以及需要继续调查的对象 |
| 材料需求 | 说明关键结论还依赖哪些函数、代码行段、资源数据或运行记录 |
| 执行记录 | 保存阶段状态、是否完成复核及修订、耗时和模型用量等信息 |

“行为角色”与“检测价值”分开判断。例如，被读取的正常系统文件可以帮助解释行为，但不一定适合作为感染指标。

## 四、最终交付内容怎么看

### 1. 行为结论按证据分层

| 层级 | 含义 | 使用方式 |
|---|---|---|
| 已确认行为 | 本次代码或已验证依赖证据直接支持所描述的能力 | 作为核心分析结论阅读；仍须结合审计结果判断引用质量 |
| 疑似行为 | 已有具体证据，但关键数据流或触发关系尚未闭合 | 结合限制说明阅读，作为后续验证重点 |
| 调查线索与附录 | 初始线索、未决冲突、历史缺口，以及未声明证据等级的旧结果等 | 作为调查和复查记录使用 |

**“已确认”指代码具备相应能力，不表示该行为已经在真实环境运行成功。**模型置信度高也不会自动将结论升级为已确认。历史缺口可能已被后续任务回答，不能直接视为当前仍未解决的问题清单。

### 2. 检测相关对象分类交付

- **感染指标（IOC）：**按对象角色和特异性规则筛出的检测对象。
- **检测特征：**有检测价值，但需要结合上下文解释和使用的对象。
- **上下文对象：**主要用于解释数据来源、系统环境或处理过程的对象。

### 3. 交付物索引

下表中的文件名均相对于一次批处理的输出目录。

| 交付物 | 主要内容 | 建议阅读对象 |
|---|---|---|
| `_final_report.md` | 已确认行为、疑似行为、IOC、检测特征、调查记录、材料建议；可用时附源码摘录 | 领导、业务负责人、分析人员 |
| `_dag_summary.json` | 各任务状态、依赖、耗时、全局整合状态及报告审计摘要 | 项目负责人、运维人员 |
| `_report_ready.json` | 与可读报告对应的结构化内容，保留完整事实字段及报告状态 | 系统对接人员、分析人员 |
| `_knowledge_audit.json` | 各原始结论和关键对象的最终去向、覆盖检查及审计问题 | 质量复核人员 |
| `_evidence_reference_audit.json` | 全局证据引用有效性及检查详情 | 质量复核人员 |
| `_global_reconciliation.json` | 全局事实集、整合状态及用量；详细决策另存于 `_global_artifacts/` | 技术负责人、分析人员 |
| `_evidence_inventory.json`、`_evidence_scope.json`、`_material_requests.json` | 已提供材料、材料范围核查和补料请求 | 分析负责人、材料提供人员 |
| `Jxx.json`、`_artifacts/Jxx/` | 单包结果、分析复核修订记录、原始输出及校验记录 | 分析人员、问题排查人员 |

建议先读中文报告，再查看批次汇总中的报告审计状态；发现问题时，可沿全局事实、单包记录回溯到对应源码。

## 五、异常处理与成本控制

| 情况 | 系统处理方式 |
|---|---|
| 模型输出格式不合规 | 先尝试程序清理和校验，必要时调用独立格式修复模型，最多3次；格式修复不得补造分析事实，发现必需字段缺失时停止修复 |
| 无法恢复完整结构 | 尝试逐项保留结构校验通过的行为和关键对象；仍无法保留时只保存原始输出，不向下游传递未经结构校验的事实 |
| 复核或修订输出结构失败 | 保留已验证的分析初稿，分别标记复核未完成或修订失败；修订范围或一致性检查失败也保留初稿 |
| 上游任务失败 | 下游收到上游不可用说明，仍可继续处理自己的材料；全局报告保留覆盖告警 |
| 全局关系模型格式修复后仍无有效结果 | 程序保守保留已有去重结论、合并关键对象，并明确标记全局语义整理未完成 |
| 接口、超时等执行异常 | 按任务或全局阶段记录失败；不能等同于前述格式失败的保守降级 |
| 报告审计发现问题 | 报告标记为证据来源不完整，批次汇总中的报告完成标记为否；保留报告与问题记录供复核 |

系统通过并发上限、请求次数、令牌预算和执行时限约束成本。核心分析、格式修复和全局整理分别统计用量；最终报告生成不调用模型。

**文件已生成、单包交付成功、全局来源校验通过、报告审计通过是不同状态，不能相互替代。**源码引用检查主要确认位置是否存在，不能单独证明语义解释正确。若未提供可用源码目录，全材料引用检查会记为未执行，应同时查看该状态。

## 六、当前能力边界与示例状态

当前系统从预先准备的文本材料包开始工作，材料拆包和依赖清单由外部提供。现有示例为16个任务，涵盖模式分派、配置处理、凭据读取、安装与注册表写入、PE映射等方向；这份示例任务清单并非所有样本的固定分析模板。

附加文件登记只说明本次材料中存在相关文件，不代表其内容已经交给模型分析。补料建议用于后续工作安排，当前主链路不会据此自动取回材料并重新分析。静态分析也不能代替动态运行验证。

完整批处理报告要求存在任务依赖清单并启用全局整合。单包运行或没有依赖清单的独立批处理只输出单包结果。已有单包结果可重新做全局整合；已有全局结果可直接重生成报告，后者不调用模型。旧的缺口整理和最终评估模型阶段不在当前自动报告主链路中。

**现有示例的实际检查情况：**本次使用当前源码，对已保存的 `results_v17` 全局结果结合 `testdata/packets` 做离线复核，未重新调用分析模型，也未改写原结果。报告中列有47条已确认行为、9条疑似行为和13项IOC；但238段证据引用中有36段未通过位置校验，10条被标为已确认的行为没有有效源码引用，报告状态为 `incomplete_provenance`，与已保存审计的问题清单一致。上述数量用于说明现有产物状态，不代表识别准确率或已验收结论。

因此，当前示例可以展示从分析到报告的流程及审计产物；正式引用其具体结论前，需要处理已标记的证据问题。
